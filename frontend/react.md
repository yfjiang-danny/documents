# React

React 最初的目的是为了解决大型、复杂 Web 应用程序的开发痛点，让创建交互式用户界面变得更简单、更高效、更可维护。它的**核心设计理念是组件化、声明式编程和数据驱动**，从而简化了 UI 的构建和状态的管理。

- 组件化: 将复杂的 UI 分解成独立的、可复用的组件，让代码更模块化，便于管理和维护。
- 声明式编程: 允许开发者通过描述 UI 在特定状态下的样子，而不是一步步告诉浏览器如何更新 UI，从而使代码更直观、更可靠、更容易调试。
- 数据驱动: 当数据变化时，React 可以高效地自动更新 UI，使得组件的状态和行为能够响应数据流的变化。
- 虚拟 DOM: 使用虚拟 DOM 来提高性能，当数据变化时，先在虚拟 DOM 中进行比较，然后只更新实际需要变动的 DOM 节点。

## React Hooks

React Hooks 是 React 16.8 引入的新特性，允许你在不编写 class 的情况下使用 state 以及其他的 React 特性。Hooks 提供了一种在函数组件中“钩入” React 特性的方式。

### 常用 Hooks

- `useState`: 用于在函数组件中添加 state。
- `useEffect`: 用于在函数组件中执行副作用操作，如数据获取、订阅或手动更改 DOM。
- `useContext`: 用于在函数组件中访问 React Context。
- `useReducer`: 用于在函数组件中管理复杂的状态逻辑。
- `useCallback`: 用于返回一个 memoized（记忆化的）回调函数。
- `useMemo`: 用于返回一个 memoized（记忆化的）值。
- `useRef`: 用于访问 DOM 元素或保存一个可变的值，该值在组件的整个生命周期内保持不变。
- `useImperativeHandle`: 用于自定义暴露给父组件的实例值。
- `useLayoutEffect`: 与 `useEffect` 类似，但它会在所有 DOM 变更之后同步调用。
- `useDebugValue`: 用于在 React DevTools 中显示自定义 hook 的标签。
- `useTransition`: 用于在渲染期间暂停更新，以避免在处理大量数据时阻塞 UI。
- `useDeferredValue`: 用于推迟更新，以避免在处理大量数据时阻塞 UI。
- `useId`: 用于生成唯一的 ID，适用于 SSR 和客户端渲染。

## Diff 算法

React 的 Diff 算法（也称为调和算法）用于比较新旧虚拟 DOM 树，以确定哪些部分需要更新。这个算法的核心思想是**最小化 DOM 操作**，通过比较新旧虚拟 DOM 树的差异，只更新实际需要变动的部分。在尽可能小的范围内，通过高效的对比策略，找出新旧虚拟 DOM 之间的差异，然后只将这些差异应用到真实的 DOM 上，从而避免整体刷新，提升性能。

### Diff 算法的核心思想

React 的 Diff 算法遵循**同层比较**的原则，但在对比子节点列表时，采用了一种**基于启发式的假设**，从而发展出与 Vue 2 的双端比较不同的策略。

#### 核心假设：React 的启发式假设

React 假设，对于大部分 UI 场景来说：

1.  组件类型相同的节点会继续使用。
2.  节点在兄弟节点之间的**移动操作**，远少于**新建/销毁**操作。
3.  通过给节点设置唯一的 `key` 属性，可以帮助算法识别哪些节点是稳定的、哪些被移动了。

基于这个假设，React 的 Diff 算法在对比子节点时，采用了一种**单次遍历、优先处理常见场景**的策略。

---

### React Diff 的具体过程（协调阶段）

当一个组件的 `state` 或 `props` 发生变化时，React 会创建一个新的 React Element 树（"新树"），然后与上一次渲染的树（"旧树"）进行递归比较，这个过程称为 **协调**。

#### 1. 比较根元素

首先从根节点开始比较。根节点的类型决定了后续的 Diff 行为。

- **场景一：元素类型不同 (e.g., `<div>` -> `<span>`)**

  - **行为**：React 会认为整个子树都是新的。
  - **结果**：**直接销毁**整个旧的 DOM 节点及其子树（包括所有子组件，触发 `componentWillUnmount`），然后**重新创建**新的 DOM 节点及其子树（触发 `componentDidMount`）。
  - **示例**：从 `<div><Counter /></div>` 变为 `<span><Counter /></span>`，即使 `Counter` 组件没变，它也会被完全销毁并重建。

- **场景二：元素类型相同 (e.g., `<div className="before">` -> `<div className="after">`)**
  - **行为**：React 会**复用**现有的 DOM 节点。
  - **结果**：仅更新该节点上发生变化的**属性**（例如这里的 `className`）。然后递归地对其子节点进行 Diff。

#### 2. 比较子节点列表（递归的关键）

这是 React Diff 最核心的部分。React 会同时遍历新旧两个子节点列表，并找出它们之间的差异。

React 采用了一种 **“双指针”但非“双端”** 的遍历策略：

1.  **第一轮遍历：处理顺序不变的节点**

    - 使用一个索引（从 0 开始），同时遍历新旧子节点列表。
    - 通过比较节点的 `key` 是否相同来判断是否为同一节点。
    - **如果 `key` 相同**：
      - 如果节点类型也相同，则复用节点，并递归进行 Diff。
      - 如果节点类型不同，则视为新节点，结束第一轮遍历。
    - **如果 `key` 不同**：**循环立即终止**，进入第二轮遍历。
    - 这个循环的目的是快速处理那些**位置没有发生变化**的节点。

2.  **第二轮遍历：处理剩余的节点（新增、删除、移动）**

    - 第一轮遍历结束后，会产生几种情况：
      - **新列表已遍历完**：说明旧列表中剩余的节点都是需要被**删除**的。
      - **旧列表已遍历完**：说明新列表中剩余的节点都是需要被**新增**的。
      - **新旧列表都有剩余节点**：这是最复杂的情况，可能涉及节点的**移动**。

3.  **处理移动的节点（使用 Key 映射）**
    - 当新旧列表都有剩余节点时，React 会创建一个关于**旧列表剩余节点**的 `Map`，键是节点的 `key`，值是节点本身。
    - 然后，遍历**新列表的剩余节点**，用它们的 `key` 去这个 `Map` 里查找。
      - **如果找到了**：说明这个节点在旧列表中存在，可以**复用**。但它的位置可能变了，需要被**移动**到新位置。React 会记录下这个移动操作。
      - **如果没找到**：说明这是一个**新增**的节点。
    - 最后，`Map` 中剩下的、没有被复用的旧节点，都是需要被**删除**的。

### Key 的重要性在 React 中的体现

`key` 是 React 识别节点身份的唯一标识。

- **没有 Key 或使用索引作为 Key（不推荐）**：

  ```jsx
  // 旧列表
  <li key=0>Apple</li> // 即将被销毁
  <li key=1>Banana</li> // 即将被更新为 Apple

  // 新列表（在头部插入）
  <li key=0>Orange</li> // 复用 key=0 的节点，内容从 Apple 更新为 Orange
  <li key=1>Apple</li> // 复用 key=1 的节点，内容从 Banana 更新为 Apple
  <li key=2>Banana</li> // 新增 key=2 的节点
  ```

  在这种情况下，React 会误以为你是更新了前两个节点的内容，然后新增了第三个节点，导致性能低下和潜在的状态 Bug（例如，输入框的内容可能会错位）。

- **有稳定且唯一的 Key**：

  ```jsx
  // 旧列表
  <li key="a">Apple</li>
  <li key="b">Banana</li>

  // 新列表（在头部插入）
  <li key="c">Orange</li> // 新增
  <li key="a">Apple</li> // 通过 key "a" 找到，直接移动
  <li key="b">Banana</li> // 通过 key "b" 找到，直接移动
  ```

  React 能精确地知道 `key="a"` 和 `key="b"` 的节点只是移动了位置，可以完美地复用它们（包括其 DOM 状态和子组件状态），只需新建一个 `key="c"` 的节点。这是最高效的方式。

### 总结：React Diff 算法的特点

1.  **深度优先，递归对比**：从根节点开始，一层层递归向下比较。
2.  **同层比较**：绝不跨层级对比，这是性能的基石。
3.  **基于启发式假设的遍历**：优先处理顺序不变的常见情况，性能更好。
4.  **强依赖 Key 进行识别**：`key` 是 React 在列表中识别节点、实现复用和移动的**唯一凭证**。一个稳定、唯一、可预测的 `key` 是高性能列表渲染的关键。

与 Vue 2 的**双端比较**算法相比，React 的算法在理论上对于列表中间位置的插入/删除操作可能不如双端比较高效，但在绝大多数实际应用中，其性能表现都非常出色，并且实现相对简单。React 团队认为，为了不常见的场景（如大量列表中间操作）而让核心算法变得复杂是不值得的。

为了高效，diff 的限制：

1. 只做同层级的比较，不做跨层级的比较。
2. 如果元素的类型不同（如从 p 变成 div），那它们就是不相同的，会销毁整个旧子树，并调用其下组件的卸载钩子，然后再创建全新的树，相当消耗性能。
3. 如果类型相同，会进行打补丁操作（如更新 className 和标签下的文本内容）

列表渲染不提供 Key 的情况：

1. 无法根据 Key 来定位元素，对于位置移动的情况，节点就无法复用，而是会根据节点位置做比较，导致性能下降。

## React 16 架构优化的核心

React 16 的优化很大程度上得益于全新的底层架构，它为解决大数据渲染的瓶颈提供了基础：

- 可中断渲染与调度：之前的 React 渲染是同步且不可中断的。当开始渲染一个大组件树时，会一直阻塞主线程，直到整个树被提交到 DOM，这很容易导致页面卡顿。React 16 引入的并发模式改变了这一点，渲染工作可以被更高优先级的更新（如用户输入）中断，这使得 React 能够更好地调度任务，优先保证用户交互的流畅性。

- 时间分片：这就像是给 React 的渲染工作装上了“休息点”。React 会将一个大的渲染任务分割成许多小任务，在浏览器的每一帧的空闲时间里执行。这样，即使数据量很大，也不会长时间霸占主线程，浏览器仍有能力响应用户的操作和渲染动画，从而维持较高的帧率。
